## What this project is

**NeuroVision-X** — 3D brain tumor segmentation on BraTS multi-modal MRI (T1, T1CE, T2, FLAIR).

Architecture: dual encoder (3D CNN + Swin Transformer) → adaptive gated cross-attention fusion → U-Net decoder → three heads (segmentation, confidence, boundary). Plus MC-dropout uncertainty, calibration analysis, and explainability.

**The research claim is reliability, not raw accuracy.** The headline result we are aiming for is "competitive Dice with substantially better calibration and boundary accuracy," not "+0.4 Dice over SwinUNETR." Design and evaluation decisions should serve that claim.

The author is new to deep learning. Explain non-obvious choices in comments and in the chat response. Prefer clear code over clever code.

Your job is to think, decide, specify, review, and teach. Implementation is delegated to Sonnet subagents. This is deliberate: Opus reasoning is reserved for design decisions and correctness judgment, while routine code generation goes to a faster model.

### What you do yourself (do NOT delegate)

### What you delegate to `py-implementer` (Sonnet)

Any new module, any substantial refactor, any file of more than ~40 lines. Write a precise spec first — file path, public API with type signatures, expected tensor shapes, edge cases, and the tests that must pass. A vague delegation produces vague code and you will have to redo it.

### What you delegate to `test-runner` (Sonnet)

Running pytest, the smoke test, or lint. Test output is verbose and belongs in a subagent's context, not yours. Ask for a summary of failures, not the full log.

### What you delegate to `code-reviewer` (Sonnet)

Read-only review of a module after implementation, before I see it. Catches shape bugs, device leaks, hardcoded paths, and missing config plumbing.

### What you delegate to `docs-writer` (Sonnet)

Docstrings, MkDocs pages, README sections, and appending to `docs/experiments.md`.

### The standard loop


## Hard constraints — do not violate these

These apply to you and to every subagent. Subagents load this file, so they are bound by it too — but restate the relevant ones in each spec, because a subagent starts with no memory of our conversation.

1. **All training code must run unmodified on a Kaggle notebook: T4 (16 GB VRAM), ~13 GB RAM, 12-hour session limit.** **The P100 is no longer usable** — measured 2026-08-01 on a real Kaggle session: the stock image's PyTorch targets sm_70+ and the P100 is sm_60, so `Tesla P100-PCIE-16GB with CUDA capability sm_60 is not compatible with the current PyTorch installation`. Request `machine_shape: NvidiaTeslaT4` in `kernel-metadata.json`. VRAM budget is unchanged (T4 is also 16 GB), and AMP is *better* on T4 — it has tensor cores, the P100 did not.
2. **No hardcoded paths, ever.** Every path comes from config. The same code runs on macOS (dev) and Linux/Kaggle (training).
3. **No CUDA-only assumptions.** Device is resolved once, from config, via a `get_device()` utility. Code must run on CPU for tests.
4. **Every training script must support full resume** — model, optimizer, scheduler, AMP scaler, epoch, global step, RNG states, and W&B run ID. Sessions get killed at 12 hours; resume is the foundation, not a feature.
5. **Mixed precision (AMP) on by default** for CUDA, off for CPU/MPS.
6. **Default patch size is 96×96×96.** Do not raise it without being asked.
7. **No new dependency without asking first.** The stack below is fixed.
8. **Every model component ships with a CPU shape test** that runs in under a second.

## Coding conventions

- Type hints on all public function signatures. Docstrings on all public functions (short, Google style).
- Config objects passed in; never read global state inside a module.
- Registry pattern for models and losses so experiments are selected by string in config.
- Logging via the `logging` module, never bare `print` in library code.
- Tensor shapes documented in docstrings as `(B, C, D, H, W)`.
- Randomness only through the seeded generator from `utils/seed.py`.

---

## Testing rules

- **Every model component gets a shape test** on tiny random tensors (e.g. `(1, 4, 32, 32, 32)`), running on CPU in under a second.
- Losses and metrics get tests against hand-computed values (perfect prediction → Dice 1.0; disjoint → Dice 0.0).
- Data pipeline tests use synthetic volumes generated in the test, never real BraTS data.
- The full suite must run on the Mac, on CPU, in under ~60 seconds. If a test needs a GPU, it does not belong in the suite.

## How to work with me

- **One module at a time.** Do not generate large multi-file implementations in a single turn, even via subagents.
- After each module: state what it does, how to run its test, and anything I should verify by eye.
- **Explain the delegated code back to me.** A subagent wrote it; I still have to understand it. Walk me through anything non-obvious in a few sentences.
- If a design decision has a real trade-off (memory vs. accuracy, MONAI vs. custom), say so and give a recommendation rather than silently picking.
- If something I ask for conflicts with the constraints above, say so instead of doing it.
- Before writing code that touches memory (models, batch sizes, caching), sanity-check it against the 16 GB VRAM budget.

### Decisions worth remembering

- **A slice viewer that indexes the volume correctly can still display the head lying on its side, and no shape test can tell.** The demo's first working render put the inferior-superior axis HORIZONTAL on the coronal and sagittal panels. Every voxel was right, every dimension assertion passed, and each panel was recognisably a brain — it just was not the view it claimed to be. BraTS carries the affine `diag(-1, -1, 1)`, so axis 0 runs right→left, axis 1 anterior→posterior, axis 2 inferior→superior; the naive "rows = first remaining axis, columns = second" mapping therefore only produces a conventional view for the axial plane, and even there it puts anterior sideways. The display convention now pinned in `app/frontend/src/lib/slicing.ts`: superior UP on coronal and sagittal, anterior UP on axial and LEFT on sagittal, patient's left on the RIGHT of the image (radiological). Found by looking at the render and confirmed by anatomy — ventricles and brainstem in the right places, corpus callosum and cerebellum visible in the sagittal — not by any assertion. Same family as the qualitative-panel bugs that only surfaced by opening the PNG.
- **The demo's geometry re-crop is verified by recomputing Dice from what the API actually serves, not by a unit test.** Saved predictions are in original BraTS geometry (240×240×155) while images and labels are cropped to the nonzero bbox, so the viewer re-crops with the case's own bbox. The check that matters: whole-tumour Dice recomputed from the served prediction and served label came to **0.9851 against the 0.9851 `scripts/evaluate.py` reported** for that case. A wrong bbox offset still renders a plausible picture, so an overlay that "looks aligned" proves nothing; matching the already-published number does.
- **A single-pass entropy field is invisible if alpha is proportional to entropy, and the fix must not touch the colour scale.** Measured on the test split: entropy sits in a thin boundary shell, only ~0.4% of voxels on a slice exceed 0.3, so `alpha = e` peaks near 0.2 exactly where the model is genuinely uncertain — the layer reads as empty. Alpha now ramps to full at 0.35 while the COLOUR stays pinned to a fixed `[0, 1]` scale, because a per-case min-max would make a barely-uncertain case look dramatic and destroy comparability between cases (the same reasoning that keeps gate maps off a per-panel normalisation). Note also that `entropy_from_logits` divides by `3 * ln 2`, so **one** region channel at maximum uncertainty reads ≈0.33, not 1.0 — the legend marks that value, the way gate maps mark 0.5, so a reader can tell the reachable part of the ramp from the part needing several channels to disagree at once.
- **The uncertainty layer is labelled from the API's `X-Uncertainty-Kind` header, and an unrecognised value must NOT fall back to the reassuring text.** The header exists so the client cannot independently decide what the quantity is; the frontend originally ignored it and called the layer "Entropy". It now shows "single pass · aleatoric + epistemic combined" only on an exact match and `unknown source (...)` otherwise. Presenting this as epistemic or MC-dropout uncertainty would be claiming a measurement the saved artifacts do not contain.
- **A dead backend behind the Vite dev proxy is an HTTP 502, not a network failure — so the "start the server" message never fired.** The client only raised `ApiUnreachableError` from a failed `fetch`, which is what happens in production single-origin mode. In development the proxy answers on the API's behalf, so stopping uvicorn produced `Failed to load the application: 502 Bad Gateway on /health` — a status code where the user needed a command. 502/503/504 are now classified as unreachable. Worth generalising: **an error path that is only reachable in one deployment mode will be tested in the other one and look fine.** Found by loading the page with the backend stopped, which is the single most likely thing to go wrong in a live demo; now pinned by `src/lib/errors.test.ts`.
- **`"val"` is a substring of `"eval"`, and that mislabelled the split in the demo header.** The default eval directory is `eval_test_baseline_unet3d`, so a `basename.includes("val")` check displayed the TEST split as "val split" — a false statement about which data is on screen, on a project that evaluates on both. Now matched as a whole word after splitting on non-alphanumerics. Exactly the trap already recorded for BraTS modality suffixes, where `"_t1" in name` is also true for `_t1ce`; it is worth assuming any short token you match against a path is a substring of some longer word in that path.

- **The calibration reporting mask must never be defined using the ground-truth label. `union_foreground_mask` was, and it manufactured 41–57% of the reported ECE.** Found 2026-08-06 on the first real calibration run (`baseline_unet3d` at epoch 130, 189 test cases) by reading the reliability table, not by any test — all 984 passed, because the code did exactly what it said. The mask was `(p >= threshold) | (label > 0)`, so a voxel below threshold could only enter it by having `label > 0`, making `P(label=1 | p < threshold, in mask)` exactly 1 **by construction**. Measured: every WT reliability bin below 0.47 had `mean_label` of exactly `1.000000`. Consequences, all of which would have gone into the paper: ECE inflated by 41% (ET) / 50% (TC) / 57% (WT); MCE ~0.99 in every region under every variant, 100% artifact and carrying zero model information; a fitted temperature of `[4.58, 4.75, 3.71]` where segmentation nets normally need 1.1–2.0; and — the tell that something was wrong — **WT ECE got WORSE under temperature scaling** (0.0730 → 0.0776), because the fit optimized NLL against the contaminated distribution. The module's own docstring had pre-emptively defended the design by analogy to Dice ("Dice is computed against the ground truth too"); that analogy is false and is now corrected in place. Dice uses the label as the object of comparison; this used the label to *select which voxels get measured* and then measured how well probability predicts that same label — selection on the dependent variable. Reported metrics now come from two label-free masks, `predicted` (default) and `brain`, both emitted in one run so they cannot drift apart. `union_foreground_mask` survives as diagnostic-only, warns on use, and stamps `circular_do_not_report: true` into `temperature.json`. The honest label-free portion of that run's ECE was ET 0.080 / TC 0.047 / WT 0.031, and the top probability bin (`mean_prob` 0.997 vs `mean_label` 0.975) shows the baseline genuinely IS overconfident — the effect the paper claims is real, it was just being measured with a broken instrument.
- **That mask fix was committed once in a state where it did not fix anything, and the commit message and a CLAUDE.md entry both said it did.** Commit `63a437b` added `predicted_foreground_mask`, `brain_mask`, the corrected docstring and the regression tests — but never changed `fit_split_temperature` or `accumulate` in `scripts/calibrate.py`, both of which still called `union_foreground_mask` directly. So every number that actually reaches a report stayed circular, behind a green 1000-test suite, a commit claiming completion, and a memory note asserting the same. The tests passed because they tested the new helper functions, not the call sites. Two rules follow. A fix to an analysis pipeline is not verified by its unit tests; it is verified by **re-running the real analysis and checking the output changed in the predicted direction** — here, that sub-threshold bins stop showing `mean_label == 1.000000`. And do not write a decision entry describing work as done while the work is still in flight; write it after verifying the artifact.
- **Corrected calibration numbers for `baseline_unet3d` @ epoch 130, test split, `predicted` mask** — the first honest calibration measurement this project has produced. Uncalibrated ECE: ET 0.0864 / TC 0.0504 / WT 0.0327 (mean 0.0565). Temperature-scaled: ET 0.0197 / TC 0.0157 / WT 0.0121 (mean 0.0158), `T = [3.08, 3.43, 2.50]`, NLL 0.330 → 0.188. MCE ~0.18–0.25 → ~0.075–0.087. Under the `brain` mask, temperature scaling makes ECE slightly WORSE (0.0028 → 0.0061) while MCE still improves 2x — the dilution effect, since 260M trivially-easy background voxels that were already calibrated get softened. That is why `predicted` is primary and `brain` is the conservative check, and it needs one sentence in the paper.
- **The calibration claim must be made against a TEMPERATURE-SCALED baseline, not an uncalibrated one.** Temperature scaling is one scalar per region, fit in seconds on CPU, and applicable to every baseline — and it cuts this baseline's ECE 3.6x, to 0.0158. "Better calibrated than an uncalibrated U-Net" therefore answers itself: a reviewer replies "then temperature-scale the baseline". The bar for NeuroVision-X is **0.0158**, not 0.0565. Consequence for the paper's structure: the calibration result probably cannot carry the headline alone, and the boundary story should lead instead — 92% of error inside 2mm, an architecture built for exactly that, and a stratified table that no one-line post-hoc method can absorb. `calibrate.py` emits both variants for every model, so the fair comparison costs nothing.
- **A predicted-positive mask is blind to false negatives, and that gap is covered elsewhere on purpose.** Voxels where the model confidently said background but tumour was present never enter a `p >= threshold` mask. That was the original (correct) motivation for the union mask, and it is a real hole — it just cannot be plugged by putting the label into the selection. It is instead covered by the boundary-stratified `bfnr_*` columns from `metrics/boundary.py`, which measure the false-negative rate directly and per distance band. When reporting calibration, cite that alongside, or a reviewer will correctly ask where the false negatives went.
- **"~92% of error lies within 2mm" was computed the wrong way. The real figure is ~74% (WT), and the correction matters.** The old number normalized the per-band error *rates* — `0.1588 / (0.1588 + 0.0137 + 0.0018 + 0.0002) = 91%` — which treats a band holding 50k voxels as equal in weight to one holding 3M. Error is counted in voxels, not in rates, so a band's rate must be multiplied by its size before any share is taken. Re-measured properly on `baseline_unet3d` @ 80 epochs / 64³, test split, per case, WT: **0–2mm 8,802 error voxels (73.7%), 2–5mm 1,672 (14.0%), 5–10mm 421 (3.5%), 10mm+ 1,052 (8.8%)**. Per region within 2mm: ET 78.6%, TC 63.1%, WT 73.7%. Two consequences, both the opposite of what the old number implied. (1) The boundary band is the *dominant* error region but not the only one — "beyond 5mm the U-Net is essentially perfect" is false; that tail is 12% of all error. (2) The 10mm+ band is **1,047 false-positive voxels against 5 false-negative** — spurious predictions far from any tumour, surviving `min_component_size: 50`, so components of real size. Its per-case median is **0.0** and its max 0.0155: a minority of cases carry all of it. That is a second, distinct, addressable failure mode, and it is exactly the one a calibration/uncertainty claim should catch — a confident prediction in tissue nowhere near a lesion is what risk-coverage and the referral curve exist to flag. Do not repeat the old framing that boundary accuracy is the only place a better model can differ.
- **The last 70 U-Net epochs bought almost nothing**, which retroactively makes the 100-epoch schedule a fair comparison rather than a handicap. Epoch-130 val vs the published epoch-200 test row: Dice ET −0.0002, TC −0.0083, WT −0.0041. Epoch *and* split both differ so this is not a clean isolation, but the magnitudes settle the worry in `docs/experiments.md` note 1 that a 200-epoch baseline unfairly outguns a 100-epoch proposed model. It does not.
- **Deterministic evaluation does not need a GPU — measured 15 cases/min on the M4 (CPU).** All 376 val+test cases of a `unet3d` run finish in ~25 minutes locally at `overlap 0.5`, producing ~3.5 GB of fp16 logits per split. That removes ~2 h of *deterministic* evaluation from the Kaggle budget entirely. MC-dropout at N=10 is 10x the passes and has not been timed locally; time it before assuming it also moves off the GPU.

- **An `eps` clamp sized for fp32 is a NO-OP in fp16, and this cost 10.5 GPU-hours.** `p.clamp(1e-6, 1.0 - 1e-6)` is exactly right in fp32. In fp16, whose epsilon is ~9.8e-4, `1.0 - 1e-6` rounds to **exactly 1.0**, so the upper clamp clamps nothing — and every probability above ~0.9995 becomes 1.0. `BranchAmbiguity` then computed Bernoulli entropy as `-(p*log p + (1-p)*log(1-p))`, so `(1-p)` was 0, `log(0)` was -inf, and `0 * -inf` was NaN. Under AMP the probes run in fp16; a probe gets that confident in ~10 epochs of real training. The NaN flowed through the gate into every fused feature and into the loss, **nothing raised**, and `neurovision` session 1 trained on NaN for 29 epochs with `best.pt` frozen at epoch 9. The fix is to compute the entropy from LOGITS, never from probabilities: with `log p = -softplus(-z)` and `log(1-p) = -softplus(z)`, `H(p) = p*softplus(-z) + (1-p)*softplus(z)`. softplus is finite everywhere, so a saturated branch gives `0 * finite = 0` — the correct entropy of a certain prediction — with no clamp, no eps and no dtype assumption. Generalize the rule: **any numerical guard written as a small constant must be checked against the dtype it will actually run in under autocast.** A test that only runs in fp32 cannot see this class of bug — `tests/test_adaptive_fusion.py::test_branch_ambiguity_entropy_is_finite_under_fp16_saturation` runs in both dtypes and was verified to FAIL against the old implementation.
- **A cheap probe must be built to reach the FAILURE CONDITION, not merely to run.** Probes v4 and v5 (3 epochs, 50 cases) validated step time, VRAM and the training loop, all correctly — and gave false assurance about a bug that needs ~10 epochs of probe saturation to appear. Two GPU-hour losses in one day share this shape: the pre-flight *read* the changed code path but never *executed* it at settings where it could fail (`git clone -b` was never run with a SHA; the entropy was never run in fp16). When designing a probe, ask what state the real run reaches that the probe will not, and force it — `probe_saturation` used 10x LR specifically to drive probes past p = 0.9995 in 20 short epochs. Corollary for pinned runs: verifying `origin/main` has a fix says nothing about the **pinned SHA**; clone the pinned tree and assert the fix is in it.

- **The gate conditions on inter-branch DISAGREEMENT, and without that it is not the contribution.** Between 2026-08-04 and 2026-08-06 the claim in `docs/research/contribution.md` and the code disagreed: the doc said the novelty is a gate conditioned on an explicit local ambiguity signal, while `GateGenerator` saw only `cat([cnn_feat, swin_proj])` — a content-only gate, which is *rung 2 of the doc's own P2 ablation ladder and its declared null result*. Gated cross-attention fusion for dual-branch medical segmentation is heavily published; the ambiguity conditioning is the only part that is not. Whenever the gate's input is changed, re-read P2 before assuming the paper still says what it says.
- **`BranchAmbiguity` probes read DETACHED branch features, and the detach is load-bearing twice over.** The probes are linear probes in the strict sense: "what does this branch, as it currently is, think the label is here?" Let gradient through and (1) the branch-supervision term pushes both encoders toward predicting the label well, hence toward *agreeing*, quietly erasing the disagreement signal the gate exists to read — the objective destroying its own input, reported later as "the mechanism doesn't work"; and (2) the segmentation loss reaches the ambiguity map through the encoders and reshapes it into whatever makes segmentation easiest, turning disagreement from a measurement into exactly the free latent quantity `contribution.md` accuses prior content-only gates of being. Same principle as the confidence head's `no_grad` target. Pinned by a pair of tests in `tests/test_adaptive_fusion.py` asserting the branch features get zero gradient from the probes while the probe weights get non-zero gradient — both are needed; either alone permits the wrong implementation.
- **Branch targets are downsampled with `adaptive_max_pool3d`, max and not average.** Adaptive because both encoders downsample with `ceil`, so a level's shape is `ceil(D / 2**k)` and a fixed-stride pool misaligns on odd inputs. Max because a small enhancing-tumor region at stride 16 occupies a fraction of one output cell and vanishes entirely under average-pooling plus a 0.5 threshold — training the probe to say "no tumor" on a case that has one. The coarse targets are therefore deliberately dilated; over-inclusion is the safer error for a signal whose only job is to produce a disagreement map. BCE only, no Dice: at stride 16 a Dice term is computed over a handful of foreground cells and is extremely high-variance.
- **`model.head.dropout: 0.1`, `model.decoder.dropout: 0.0`, and this could not be decided later.** Dropout placement is a training-time choice, so a checkpoint trained at 0.0 can never be given a meaningful epistemic map afterwards. Before this, the CNN encoder was the *only* MC-dropout source and a weak one — its `Dropout3d` sits before `conv2 -> norm2` and `zero_init_residual` zeroes `norm2.weight`, so at init the perturbation is multiplied by exactly zero and mutual information is 0 at every voxel (measured). The segmentation head is the classic placement: immediately before the 1x1x1 logit conv, perturbing the prediction without degrading any intermediate feature, three such heads under deep supervision, and unreachable by a zeroed norm. The decoder stays at 0.0 because `Dropout3d` drops WHOLE CHANNELS and doing that at full resolution trades away boundary detail — the half of the research claim the paper is actually about.
- **`grad_clip_norm: 1.0` is a live confound for the P2 comparison and must be settled from the timing probe, never mid-run.** Measured at init on random input: `neurovision` 1.629, `ablation_content_only_gate` 1.776 — both above the clip threshold. Clipping scales the WHOLE gradient, segmentation term included, so two runs that clip at different rates are running at different effective segmentation learning rates and the ablation is no longer isolating the ambiguity signal. Read `train/grad_norm` (already logged) during the 2-epoch probe; if it sits above 1.0 routinely, raise the clip to 5.0 for ALL runs in the comparison before any of them starts.
- **The GPU budget is 60 h, single seed, and the cuts are recorded in `docs/experiments.md`, not here.** The ranking decision behind them: the contribution ablation outranks baseline breadth, so `baseline_swinunetr` (~25 h, 42% of the budget) is cut in favour of `ablation_content_only_gate`. Consequence to state in the paper rather than discover in review — there is no transformer baseline on our splits, and published SwinUNETR BraTS-2021 numbers are not a substitute because those are on the official validation set while ours is a random split of the training set. Single seed also means no seed-to-seed std, so no claim may rest on a margin smaller than noise we cannot measure.

- **Gate maps display with NEAREST-NEIGHBOUR upsampling and a colour scale fixed to `[0, 1]` with 0.5 marked.** A stride-8 gate is a 12³ map inside a 96³ patch; a smooth upsample renders it as if it had voxel precision, the same hazard `gradcam.py` flags about an upsampled CAM. And the gate is a sigmoid that `GateGenerator` initializes centred on 0.5 (no prior toward either branch), so a per-panel min–max would make a gate that barely moves off its init look dramatic, and two levels behaving completely differently look identical. Both pinned by tests.
- **`plot_band_profile`'s x axis is CATEGORICAL, not a continuous distance axis.** The final band is `[10, inf)`, which has no finite midpoint — placing it on a mm axis means inventing a position for an unbounded bin, and visually compressing or stretching every other band relative to it. Serves both the boundary-error and the gate-vs-boundary figure so they cannot drift apart visually.
- **Integrated Gradients maps render SIGNED, on a diverging colormap centred at zero.** Negative attribution is evidence *against* the region; a sequential colormap renders "argues strongly against" and "not involved" identically. Grad-CAM with `relu=True` is non-negative and belongs on the sequential map — hence `plot_attribution_panel`'s `signed_keys`. Per-cell normalization is right here (unlike gate maps, which have a meaningful absolute scale) because attribution magnitudes are not comparable across methods or cases.
- **`plot_modality_attribution` RAISES on integer region values rather than mapping them.** There are two live region orderings and they disagree: `figures.REGION_ORDER` is `("WT", "TC", "ET")` (reporting) while `data.transforms.REGION_NAMES` is `("ET", "TC", "WT")` (the model's channels, and what `scripts/explain.py` writes into `modality_attribution.csv`). Index 0 therefore means ET in the file and WT in the plotting module, and either mapping produces a perfectly plausible chart with every bar relabelled. `figures.py` cannot import `REGION_NAMES` to settle it (torch), so it refuses to guess — same reasoning as `metric_direction` raising on an unknown metric. The notebook maps it explicitly.
- **A hatch must never be drawn in its own bar's face colour.** Matplotlib renders hatching in the EDGE colour, so `edgecolor == facecolor` paints the marks invisibly — while the artist still reports a hatch (so a `get_hatch()` assertion passes) and the legend goes on advertising a mark that is not on the figure. Found by looking at the PNG, which is the only way this class of bug surfaces; now taken from `rcParams["axes.edgecolor"]` so it stays visible under a dark render, and pinned by a test comparing face against edge. Legend headroom is reserved by expanding the y limit BEFORE placing the legend, for the same reason `plot_qualitative_panel` uses `loc="outside lower center"`: `loc="best"` can only avoid the data if there is somewhere to go.
- **`build_boundary_table` and `build_results_table` agree on what `n` means** — total case count, with `n_missing` the NaN count inside it. They live in one module and feed one paper; a column name meaning "total" in one table and "contributing" in the other is a wrong denominator in an "averaged over N cases" claim, with nothing failing. Pinned by a test asserting the two builders agree. Boundary band ordering is NUMERIC, not lexicographic — a string sort puts `"10-inf"` before `"2-5"` and silently reverses the reading order of every boundary table.
- **`risk_coverage.csv` saves the oracle ceiling and the random null alongside the model curve.** A risk-coverage figure cannot be read without them: the oracle is the bound no uncertainty estimate can beat, and a model curve hugging the random line means the uncertainty carries no information about case difficulty — a real, reportable negative result that nothing else in the saved output would reveal. Same reasoning as `compare_methods`' automatic `random` row in the faithfulness table.
- **`scripts/calibrate.py` takes TWO eval directories and has no single-directory mode.** Temperature is fit on val and applied to test; fitting and reporting on one split fits `T` to that split's own noise, and that number *is* the paper's headline. The rule is enforced structurally — the script raises when `fit_dir` and `apply_dir` resolve to the same path — because a convention documented only in a docstring is one hurried CLI override away from being violated with nothing failing anywhere. Practical consequence: **every model needs `scripts/evaluate.py` run on val AND test**, not test alone.
- **The temperature fit samples RAGGED per channel and fits each channel with its own 1-D `fit_temperature` call.** The obvious implementation builds a rectangular `(N, C)` sample, which forces truncating every channel to the smallest count achieved. Two invisible consequences: ET's reporting mask is routinely a fraction of WT's, so ET silently dictates the sample count for all three regions; and a case with no enhancing tumor (2.6% of BraTS 2021) contributes **zero** voxels to the fit, including its perfectly usable TC and WT ones. `fit_temperature`'s own docstring notes the joint fit is mathematically identical to `C` independent per-channel fits (the losses are additively separable), so the 1-D route costs nothing and removes the constraint. `tests/test_calibrate_script.py` recovers a known per-channel temperature (1.0 / 2.0 / 0.5) from deliberately unequal sample counts.
- **The reporting mask is computed once from the UNCALIBRATED probabilities and shared by both calibration variants, in ONE pass over the split.** Sharing it matters because the two variants must cover exactly the same voxel set or their ECEs are not comparable — and at `threshold = 0.5` recomputing it is provably a no-op (temperature scaling is strictly monotone), which is precisely what makes a recompute dangerous: it stops being a no-op the moment the threshold moves, and the resulting mismatch reads as a calibration effect. One pass rather than two also avoids re-reading ~10 GB of logits and retaining ~1.9 GB of per-case masks on a 189-case split.
- **`calibrate.py` refuses to fit a temperature from `probabilities/` at all.** fp16's gap below 1.0 is 0.000488, so any probability above ~0.99976 round-trips to exactly 1.0 and its logit is `+inf`. A trained net is that confident across most of the tumor core, so a fit from saved probabilities would have to drop or clamp exactly the voxels that drive miscalibration — biasing `T` toward 1.0 and understating overconfidence, with nothing failing anywhere. The saturation is one-sided (fp16 subnormals reach 6e-8, so `p → 0` survives), and ECE/MCE/Brier and the reliability diagram are unaffected either way — 0.9998 and 1.0 fall in the same bin. So the *uncalibrated* half of the analysis is perfectly valid from probabilities; only the fit is not.
- **A diverged LBFGS fit returns `None` and is recorded in `temperature.json` with `converged: false` and a reason, rather than raising.** The uncalibrated half of the analysis is still valid and should still be written; what must never happen is a scaled row reaching the reported table from an unusable fit. Writing the reason to a *file* matters too — a missing scaled row has to be explainable months later, not only from a terminal log nobody kept.
- **Boundary bands stratify on the GROUND-TRUTH distance field, never the prediction's.** If each model's own output defined the bins, two models would be binned by two different partitions of space and their per-band numbers would not be comparable — which is the entire purpose of the table. Bands are half-open `[lo, hi)` and no voxel sits at distance exactly 0 under the signed convention (a voxel immediately inside the surface is `-1`, immediately outside `+1`), so there is no boundary voxel to double count.
- **`signed_distance_to_boundary` returns all-NaN for an empty OR full mask, and this is load-bearing.** `scipy.ndimage.distance_transform_edt` does not raise on an array with no zeros (or no nonzeros) — it returns a meaningless filled array. That NaN is the mechanism by which an absent region propagates to NaN metrics instead of to a plausible wrong number, and `boundary_band_masks` relies on NaN comparisons being False so a degenerate region lands in no band at all.

- **Never use `monai.losses.DiceCELoss` for the region targets.** Its `forward` picks the CE term by channel count — `self.ce(...) if input.shape[1] != 1 else self.bce(...)` — so with 3 region channels it applies softmax cross-entropy even when constructed with `sigmoid=True`. Softmax pushes ET/TC/WT to be mutually exclusive, but they are nested. Use `neurovision.losses.segmentation.DiceBCELoss` (`DiceLoss(sigmoid=True)` + `BCEWithLogitsLoss`), which scores exactly 0 on a perfect prediction.
- **`smooth_nr` must stay non-zero** (1e-5, equal to `smooth_dr`). With `smooth_nr=0`, a correctly predicted *empty* region scores Dice 0 — measured loss 1.000, the worst possible — for the right answer. Many BraTS cases have no enhancing tumor, so this would push the model to hallucinate it.
- **The real training batch is `batch_size × samples_per_volume`, not `batch_size`.** `RandCropByPosNegLabeld` returns a LIST of `samples_per_volume` crops per case (even at 1), so `scripts/train.py` must pass `collate_fn=monai.data.list_data_collate` — plain `default_collate` produces a list of per-position dicts and `batch["image"]` raises `TypeError` on the first step. `list_data_collate` flattens the list, so `batch_size: 2` with `samples_per_volume: 4` sends **8** patches of 96³ per step. Verified: `(8, 4, ...)`. That is ~4× the activation memory the `batch_size: 2 # 16 GB VRAM` comment assumed and OOMs SwinUNETR-B on a P100. Standard MONAI BraTS recipe is `batch_size: 1` with `samples_per_volume: 4`.
- **Gradient accumulation flushes at epoch end.** When batch count is not a multiple of `grad_accum_steps`, the trailing window never triggers a step — and without an explicit flush its gradients are neither applied nor zeroed, so they survive into the next epoch and are summed into its first step. Silent: nothing errors, the gradients are just wrong at every epoch boundary.
- **`scaler.unscale_` must run before `clip_grad_norm_`.** Gradients stay multiplied by the AMP scale factor (starts at 65536) until `unscale_`. Clipping first compares a ~65536× inflated norm against `grad_clip_norm: 1.0`, so every step gets clipped to nearly nothing and the model silently stops learning.
- **Resume order in `scripts/train.py` is checkpoint-then-W&B, deliberately inverted.** `wandb.init(id=..., resume="allow")` needs the run id, which only exists after the checkpoint is read. Initialising W&B first creates a fresh run and orphans the one the checkpoint belongs to. Hence `Trainer(..., wandb_run=None)` then `trainer.wandb_run = run`.
- **Checkpoints are written atomically** — temp file in the *same* directory, then `os.replace`. A SIGKILL partway through a 754 MB `torch.save` would otherwise leave a truncated `last.pt` that has already replaced the good one, losing the whole run. Same directory matters: `os.replace` is only atomic within one filesystem. Not fsync'd — the threat model is process SIGKILL at the 12-hour limit, which does not lose page cache; fsync would only add protection against kernel panic, at 1-3s per epoch.
- **Checkpoints must stay `weights_only=True`-loadable.** torch 2.13 defaults `torch.load` to `weights_only=True`, and a payload holding an OmegaConf `DictConfig` or numpy's RNG ndarray fails with `UnpicklingError: Weights only load failed`. So the config is stored as a resolved YAML *string* and numpy's RNG state as a dict with the array as a tensor. `weights_only=False` would work but makes loading any checkpoint arbitrary code execution. `tests/test_checkpoint.py` has a direct `torch.load(..., weights_only=True)` regression guard — if it fails, someone added an unsafe object to the payload.
- **`start_epoch = saved_epoch + 1`.** The saved epoch already completed; resuming *at* it retrains that epoch and desynchronizes the epoch-indexed LR schedule (including `warmup_epochs`), silently training something the config no longer describes.
- **Resume is epoch-granular, not step-granular.** Dataloader position within an epoch is not recoverable with `num_workers > 0`, so a kill mid-epoch loses that epoch. `save_every_n_epochs: 1` caps the loss at one epoch — keep epochs short enough that this is acceptable.
- **Checkpoint sizes: unet3d ~155 MB, SwinUNETR-B ~754 MB** (weights + Adam's two fp32 moment buffers; AMP does not shrink these). Periodic snapshots every 10 epochs over 300 epochs would be ~22.6 GB, past Kaggle's 20 GB `/kaggle/working` quota — hence `keep_last_n`, which globs only `epoch_*.pt` and sorts numerically so `last.pt`/`best.pt` can never be pruned.
- **`best_metric_mode` is stored in the checkpoint.** Dice and IoU are maximized; loss, HD95 and ECE are minimized, and the calibration claim rests on the minimized ones. A `best_metric` fallback of `-inf` under a minimized metric means nothing ever compares as better and `best.pt` silently stops updating for the rest of the run, so the fallback sentinel follows the mode.
- **Model `out_channels` is 3, never 4.** 4 is the raw *class* count `{0,1,2,3}` and also the modality count (`in_channels`), so it is easy to write by accident. The heads are 3 sigmoid channels over the nested ET/TC/WT regions; a 4-channel head makes `BCEWithLogitsLoss` raise against the 3-channel target on the first step. Both model configs interpolate `out_channels: ${data.num_classes}`.
- **SwinUNETR requires inputs ≥ 64 voxels on every axis.** It downsamples 32×, so a 32³ input reaches the bottleneck at 1³ and `InstanceNorm3d` raises `ValueError: Expected more than 1 spatial element when training`. `.eval()` does not help — `InstanceNorm3d` has `track_running_stats=False` and computes per-instance statistics in eval too. The 96³ training patch is fine (3³ bottleneck); this only constrains shape tests, which is why `tests/test_models.py` uses 32³ for the U-Net but 64³ for Swin, at `feature_size=12` (production 48 takes 1.84s forward on CPU, over the suite's budget).
- **`zero_init_residual` makes `conv2` receive a gradient of exactly zero on the first optimizer step. That is expected, not a dead layer.** Zero-initializing `norm2.weight` in each `ResidualBlock` makes the residual branch output 0, so the block starts as an exact identity — a standard stabilizer for residual nets. But GroupNorm computes `weight * normalized + bias`, so the gradient reaching `conv2` is scaled by that same zero. `norm2.weight` itself gets a non-zero gradient, moves off zero after one step, and `conv2` trains from step 2 onward. A zeroed `conv2` row in a step-1 gradient histogram is therefore correct behaviour. `tests/test_cnn_encoder.py::test_zero_init_gives_conv2_zero_grad_on_first_step_only` pins both halves. The trick's benefit scales with depth and this encoder is shallow (~7 blocks), so it is a flag rather than a hardcoded default — ablate it if early training looks fine without it.
- **The two encoder branches agree on spatial shape at every level, including odd sizes — measured, not assumed.** `CNNEncoder` downsamples with padded stride-2 convolutions giving `ceil(D/2)`. MONAI's Swin downsamples by patch merging, which *looks* like it would truncate — but `PatchMergingV2.forward` pads first (`pad_input = (h % 2 == 1) or ...; x = F.pad(x, (0, 0, 0, w % 2, 0, h % 2, 0, d % 2))`), so it also produces `ceil(D/2)`. Verified equal across 96³, 64³, 100³, 90³, 33×35×37 and anisotropic shapes: CNN levels 1..4 match Swin outputs 0..3 exactly. (An earlier version of this entry claimed they diverge at odd sizes and that 96³ was therefore load-bearing for shape reasons — that was wrong, and would have discouraged patch-size ablations for no reason.) The alignment test in `tests/test_swin_encoder.py` is what keeps this true across MONAI upgrades; do not delete it.
- **The Swin branch has no stride-1 feature, and cannot be given one.** `patch_embed` downsamples 2× before any attention runs, so Swin's pyramid is strides 2/4/8/16/32 while the CNN's is 1/2/4/8/... Making Swin emit stride 1 would need `patch_size=1`, i.e. attention over 884,736 tokens at 96³ — an instant OOM, and it discards every pretrained checkpoint. This is not a limitation to work around: SwinUNETR itself never fuses a transformer feature at full resolution (its `encoder1` is a plain conv on the raw input). So the full-resolution CNN level 0 stays **CNN-only** and passes to the decoder unfused, and fusion happens at strides 2/4/8/16 where both branches exist.
- **`einops` is a hard requirement for SwinUNETR**, not an optional extra — `SwinUNETR.forward` calls `einops.rearrange`, so a missing einops fails at *run* time with `OptionalImportError`, not at import. Pinned in `requirements.txt`; the Kaggle image already ships it.
- **`use_checkpoint: true` by default for SwinUNETR.** At 96³, batch 2, AMP: params+Adam+grads ≈ 1.0 GB, activations ≈ 11-13 GB without checkpointing (~13 GB total, no headroom on a 16 GB P100) vs ≈ 4-6 GB with it. Costs ~20-30% step time. Turn it off only at `batch_size: 1`.
- **Fusion cross-attention is WINDOWED, and that is a memory decision, not a modelling preference.** At the finest fused level (stride 2) a 96³ patch is 48³ = 110,592 tokens. Measured against the 16 GB budget at B=4, fp16, 4 heads: full attention needs 110592² × 16 ≈ 2×10¹¹ score entries (impossible); pooled-KV / spatial-reduction attention (PVT-style, r=4) needs ≈ 6.1 GB; non-overlapping 4³ windows need ≈ 226 MB. Windowed wins by ~27× over the obvious alternative. The cost — cross-attention itself sees no global context — is acceptable *specifically here* because keys/values come from the Swin branch, which already did shifted-window global mixing across its own stages; cross-attention's job is aligning CNN geometry against context Swin already built, not building it. `WindowedCrossAttention` additionally uses `F.scaled_dot_product_attention`, whose backends never materialize even that 226 MB. Do not "improve" this to global attention without redoing these numbers.
- **`full_attention_max_tokens` (default 512) is a runtime rule, not a per-level hardcode.** A level whose feature map has at most that many voxels gets ONE window equal to the whole map — which *is* full global attention, so both regimes share one code path and cannot drift apart. At 96³ this fires only at stride 16 (6³ = 216 tokens, a 1.5 MB score matrix). Consequence: the attention pattern depends on input shape, which is why the block has no relative-position-bias table (a table sized to a fixed window would break the rule). Safe because inference is fixed-size sliding-window over 96³ patches.
- **Estimated fusion activation memory at 96³, B=4, fp16 (measured-by-hand, before any GPU run):** ~790 MB at stride 2, ~200 MB at stride 4, ~50 MB at stride 8, ~8 MB at stride 16 — **~1.05 GB total**, from ~14 feature-map-sized tensors kept per block for backward. `use_checkpoint: true` on the fusion blocks drops that to ~150 MB for ~30% step time on those blocks. `gate_channels: "channel"` adds ~113 MB at stride 2 alone, which is why `"scalar"` is the default (it is also the interpretable one — a per-voxel gate map is directly plottable for the paper).
- **The fusion merge is `cnn + layer_scale * gate * attn`, never `gate * cnn + (1 - gate) * swin`.** The CNN branch carries the full-resolution detail the boundary-accuracy claim rests on and must never be attenuated by a learned gate. Under this form the gate means exactly one thing — how much transformer context is admitted at this voxel — which is what makes the gate map a publishable figure rather than an uninterpretable blend coefficient. `layer_scale` is a `(1, C, 1, 1, 1)` parameter initialized to 1e-4 (same reasoning as `zero_init_residual` in `cnn.py`); at exactly 0.0 the block is an EXACT identity, so "fusion off" in the ablation is literally the CNN-only network, not an approximation of it.
- **`GateGenerator` zero-inits its output conv's BIAS but deliberately not its WEIGHT.** Bias-zero centres the gate on sigmoid(0) = 0.5 (no prior on either branch); the random weight leaves a spread (measured ~0.27-0.73 on random input, mean ~0.50). Zeroing the weight too would make the gate flat 0.5 everywhere — and since `layer_scale` already starts the block as a near-identity, that would remove the only source of spatial symmetry-breaking in the thing whose entire job is to vary spatially.
- **`_window_partition`'s row order is batch-major and the key-padding mask depends on it.** The mask is built once on a batch-invariant `(1, Dp, Hp, Wp, 1)` validity grid and tiled with `.repeat(B, 1, 1)`; if partition rows were window-major instead, the mask would align with the wrong windows and only the padded border would be wrong — invisible to every shape test. Note the whole class of bug here: a wrong permute inside `_window_partition` would group spatially scattered voxels into a "window", `_window_reverse` would still undo it cleanly, and every shape assertion would still pass while attention ran over nonsense. `tests/test_adaptive_fusion.py` pins this with a coordinate-encoding contiguity test, an exact round-trip, a batch-major ordering test, a B>1 no-cross-batch-leakage test on the padded path, and a hand-rolled `softmax(qk/√d)v` oracle — the last being the only test in the file that checks the attention math against something other than the module itself. Do not delete these.
- **`NeuroVisionX.forward` returns a `Tensor` OR a `list[Tensor]`, and the switch is `self.training and deep_supervision_levels > 1`.** Two independent things force this. Sliding-window inference (and MONAI's inferer) call `model(patch)` and expect a tensor, so eval must never return a list. `DeepSupervisionLoss.forward` takes a sequence ordered HIGHEST RESOLUTION FIRST and upsamples each entry to the target internally, so `[full_res, stride2, stride4]` is already the order it wants — do not reverse it. **MC-dropout hazard:** uncertainty estimation re-runs the network with dropout active, and doing that by calling `model.train()` flips the return type and breaks sliding-window inference. Enable the `Dropout3d` modules individually and leave the model in `eval()`.
- **`model.deep_supervision_levels` and `training.loss.deep_supervision.enabled` must agree, and `build_neurovision` raises if they do not.** A model emitting a list into a loss expecting one tensor is a crash; the reverse (one output, `DeepSupervisionLoss` wrapper) silently reduces to the plain loss and quietly trains something the config does not describe. The check is skipped when there is no `training` group at all, so model-only test configs still build. Consequence worth knowing: `model=neurovision` does NOT compose against the stock training config, which has deep supervision off for the single-output `unet3d` baseline. Use `+experiment=neurovision`, which turns it on — deliberately not flipped in `training/default.yaml`, so the baselines keep composing unchanged.
- **The decoder's `_match_spatial` crops from the END of each axis, never centre.** Both encoders halve with `ceil` and pad at the end, so `2 * ceil(n / 2)` overshoots the skip by at most one voxel and that voxel is the trailing pad. A centre crop would shift every decoder feature half a voxel against its skip and compound up the ladder — a segmentation systematically offset from the image, with plausible output and no shape test ever failing. It raises when the mismatch exceeds 1 voxel per axis, which means a skip list from a different network rather than a rounding effect. Pinned by a content test (arange values, checks the LEADING values survive) and end-to-end on an odd anisotropic pyramid.
- **Decoder attention gates default OFF, on purpose.** The novel contribution is the fusion module. Turning on a second attention mechanism by default makes it impossible to attribute a Dice gain to the fusion block rather than to the gates. `use_attention_gates` exists to be ablated, not to be on. (They also gate at the skip's resolution using the already-upsampled decoder feature, so nothing is resampled inside the gate — Oktay et al.'s original uses a coarser gating signal and resamples internally.)
- **Decoder upsampling is `ConvTranspose3d` by default with `upsample: interp` as an escape hatch.** Transposed convolution is learnable and is what nnU-Net and SwinUNETR use, but its overlapping kernel footprint can checkerboard — periodic texture along a boundary. This project's headline claim is boundary accuracy, so `interp` (trilinear + 1x1x1 conv, cannot checkerboard, costs more memory since it interpolates at the input width) exists specifically to rule that out if HD95 ever looks periodic.
- **Measured activation memory of the full model at 96³ (saved-tensor bytes via `torch.autograd.graph.saved_tensors_hooks`, B=1, fp32, on CPU — real numbers, not arithmetic).** Baseline 4.53 GB with only the Swin branch checkpointed (the config default). Each lever, measured individually: CNN encoder checkpointing −1.58 GB, decoder −1.25 GB, fusion −0.51 GB; CNN + decoder together 1.70 GB total; all three 1.19 GB total. Convert to AMP by roughly ×0.5-0.6 (not exactly half — norm layers stay fp32 under autocast) and multiply by the real batch. Add ~0.56 GB for fp32 weights + grads + Adam's two moments (AMP does not shrink these) and ~1 GB for CUDA context, cuDNN workspace and allocator fragmentation.
- **The batch that matters for this model is `batch_size × samples_per_volume`, and at 96³ that is what decides whether it fits. The `B=1` in the entry above is ONE PATCH, not one optimizer step — an earlier version of this entry conflated the two and understated the real step by ~3.5x.** Re-measured 2026-08-08 with the same `saved_tensors_hooks` method on the production `+experiment=neurovision` config: **4.58 GB at 1 patch, 8.86 GB at 2 patches**, i.e. linear at ~4.28 GB/patch over a ~0.30 GB fixed term. So the project default `batch_size: 1` is **4 patches/step ≈ 17.4 GB of fp32 activations**, not the "~4.5-5.5 GB" this entry used to claim. Under AMP (×0.5-0.6) that is ~8.7-10.5 GB, plus ~0.56 GB weights/grads/Adam and ~1 GB context and fragmentation: ~10-12 GB against a nominal 16 GB T4. **That prediction was WRONG and the run OOM'd — measured on a real T4 2026-08-08.** Two reasons, both worth carrying forward. A T4's usable capacity is **14.56 GiB, not 16**; ~1.4 GiB is CUDA context and reserve, so the budget to compare against is 14.56. And the AMP conversion factor for *this* architecture is **~0.75+ of fp32, not 0.5-0.6** — the run reached 14.22 GiB partway through a single forward pass and died there, so the un-checkpointed 4-patch peak is well above 14.56 GiB. Do not apply the 0.5-0.6 rule of thumb to this model. The fix is `model.encoder.cnn.use_checkpoint=true`, which drops the per-patch figure from 4.58 to ~2.95 GB fp32. `batch_size: 2` (8 patches) is ~35 GB fp32 / ~19-21 GB AMP and cannot fit at all without checkpointing. Turning on CNN + decoder checkpointing (~20-30% step time each) is the cheapest lever and buys back more than the fusion block's does: `model.encoder.cnn.use_checkpoint=true model.decoder.use_checkpoint=true`. The `neurovision` config ships with **only the Swin branch checkpointed**; the other three flags are false.
- **Metrics use `ignore_empty=False` (the BraTS convention):** a region absent from the ground truth scores Dice 1.0 if the prediction is also empty, 0.0 if it predicted anything. **Measured on our actual data (BraTS 2021 training, 1251 cases): 33 cases, 2.6%, have zero enhancing tumor** — not the ~35% widely quoted for BraTS and previously asserted in this file. That figure does not hold for the 2021 training set, which is overwhelmingly high-grade glioma. So the convention moves headline ET Dice by well under a point here, rather than by several. It still must be stated in the paper — the choice is invisible otherwise — but it is not the load-bearing caveat this file used to claim. (43 cases, 3.4%, have zero necrotic core; no case has an entirely empty label.) Re-measure if the dataset ever changes: `metadata.csv` column `n_class_3`. `compute_case_metrics` therefore also emits a `gt_empty_<region>` flag per case, so the ignore-empty mean can be recomputed from the saved per-case table without re-running inference — and `summary().loc["gt_empty_ET", "mean"]` gives the fraction of the eval set where ET Dice is empty-vs-empty scoring rather than real overlap.
- **HD95 empty-case handling is ours, not MONAI's.** `compute_hausdorff_distance` returns NaN for all three degenerate cases (both empty, either side empty) and cannot distinguish them. `hd95()` overrides both-empty to **0.0** — correctly predicting "no tumor here" is not a boundary error and must not vanish from a NaN-skipping mean — and leaves one-sided-empty as NaN, counted in `summary()`'s `n_missing` column. Deliberately not the old BraTS 373.13mm penalty, which turns HD95 into a high-variance Dice proxy and would undercut the boundary-accuracy claim.
- **Splits are frozen once written** (`configs/data/splits.yaml`). Adding cases later raises rather than reshuffling val/test under an already-reported result; regenerating takes an explicit `overwrite=True`.
- **The bootstrap in `analysis/statistics.py` resamples CASE INDICES into the difference array, never the two score arrays independently.** Independent resampling measures the spread of each model's absolute Dice (large — driven by easy vs hard cases) instead of the spread of the paired difference (small), so it would widen every interval and hide real effects. `tests/test_statistics.py` pins it with a case where all per-case differences are exactly +0.05 but the raw values vary widely: the paired CI is narrower than 0.01, an unpaired one would not be.
- **`metric_direction` RAISES on an unknown metric rather than defaulting to higher-is-better.** A silently wrong direction on HD95 or ECE inverts a paper claim with nothing failing anywhere. For the same reason `compare_models` emits an `improvement` column signed so positive always means "A is better", regardless of the metric's own direction — a reader never has to remember the convention per row.
- **Wilcoxon, not a paired t-test, and both are reported alongside the bootstrap CI.** Per-case Dice is bounded, left-skewed and heavy-tailed (a handful of catastrophic cases), so the t-test's normality assumption does not hold; Wilcoxon only needs symmetry of the differences. When the CI and the p-value disagree, that disagreement is itself a finding and `verdict` resolves it conservatively — `inconclusive` if EITHER the CI contains 0 or Holm-adjusted p > alpha.
- **The Holm family is one `compare_models` call, and it must be fixed BEFORE looking at p-values.** ~9-12 tests per baseline comparison (3 regions × several metrics) would produce a false positive in roughly every other table uncorrected. Holm is uniformly more powerful than Bonferroni and assumes nothing about independence. Running the table, seeing one metric fail, and re-running on a smaller metric set silently destroys the error-rate guarantee.
- **Exact ties are a real effect here, not a corner case.** Under `ignore_empty=False`, every case with an empty ground-truth ET region scores Dice exactly 1.0 for any model that also predicts empty, so two different models tie exactly there. `zero_method="wilcox"` (scipy's default) discards those pairs, so the test runs on a smaller, non-obvious subset — hence the reported `n_zero` / `n_effective` and a warning above 50% ties. When ALL differences are zero, `wilcoxon_signed_rank` short-circuits to `pvalue=1.0` BEFORE calling scipy: scipy raises on small samples but at n≈30 takes its normal-approximation path, divides 0/0 and returns a **NaN p-value** with only a RuntimeWarning, which would then propagate into the Holm correction.
- **`compare_models` averages each model over the PAIRED-COMPLETE subset, not each column's own non-NaN values.** HD95 is legitimately NaN when exactly one side of a region is empty, and those NaNs need not fall on the same cases in both tables — averaging independently makes `mean_a - mean_b` disagree with `mean_diff` (measured -1.173 vs -1.130 on a 30-case table with a single one-sided NaN), which reads as an arithmetic error in the paper's table.
- **There is no argmax anywhere in inference.** The heads are 3 *overlapping* sigmoid regions, so argmax is wrong twice: the channels are not mutually exclusive (a voxel is legitimately 1 in all three), and argmax forces every background voxel into some region instead of allowing "none of the above". Discretization is sigmoid + per-channel threshold; `postprocess.regions_to_classes` is the inverse of `metrics.classes_to_regions` and is what produces the `{0,1,2,3}` map. Its assignment order is outer-to-inner (`WT`→2, then `TC`→1, then `ET`→3) so the inner region overwrites — reversed, WT paints class 2 over every ET voxel and enhancing tumor silently vanishes from the output.
- **`enforce_nesting` unions inner into outer, never intersects.** Intersection would delete a confidently-predicted ET voxel because the lower-confidence TC channel missed it there — discarding the model's strongest signal to satisfy its weakest. It runs LAST in `postprocess_logits` because raw thresholded output was never nested to begin with (three independent heads), and `keep_largest_component` can additionally pick a different largest component per channel. Note `remove_small_components` alone does *not* break valid nesting: containment is monotonic, so a surviving ET component sits inside a TC component that is at least as large.
- **`MONAI KeepLargestConnectedComponent()` must be given `applied_labels` explicitly.** Its default auto-detection calls `get_unique_labels(img, is_onehot=True, discard=0)`, which unconditionally discards channel *index* 0 — correct for a label map where value 0 is background, wrong here where channel 0 is ET. Left at the default, a case where ET is the only non-empty channel is silently skipped entirely. Same family as the `ConvertToMultiChannelBasedOnBratsClassesd` trap.
- **Evaluation metrics are computed in CROPPED space, predictions are saved UNCROPPED.** The ground-truth `label.npy` is already cropped, and uncropping both sides adds identical background to numerator and denominator — Dice and HD95 come out numerically identical, just slower. Uncropping matters only for the saved artifact, which has to be valid BraTS geometry. `uncrop_to_original` raises when the bbox extent disagrees with the array's spatial shape: that means prediction and `meta.json` came from different preprocessing runs, and placing it anyway yields a spatially shifted submission that looks entirely plausible.
- **`evaluate.py` moves both tensors to CPU before `add_case`.** `regions` is on `device`, `batch["label"]` comes straight off the DataLoader on CPU. Passing them as-is raises a device mismatch inside MONAI's `compute_dice` — but only on CUDA. On a CPU box they agree by accident and the whole suite passes, so no test can catch this class of bug; it is pinned by comment. CPU rather than `device` also keeps HD95's intermediate buffers over a ~240³ volume off the 16 GB budget.
- **HD95 needs `spacing` passed from `meta.json`**, or it is reported in voxels, not millimetres. The boundary-accuracy half of the research claim is a millimetre claim. Note `Trainer.validate` does NOT pass spacing — its HD95 is in voxels and is for monitoring only; the reported numbers come from `scripts/evaluate.py`, which does.
- **`map_location=str(device)` puts the RNG state tensors on CUDA too.** `load_checkpoint` maps the WHOLE payload, and the numpy RNG state is stored as a torch tensor (to keep `weights_only=True` loadable). So on a GPU resume, `saved["state"].numpy()` raises `TypeError: can't convert cuda:0 device type tensor to numpy`, and one line later `torch.set_rng_state` rejects a non-CPU ByteTensor. Both restore paths now `.cpu()` first. Measured on Kaggle 2026-08-02 resuming a real run at epoch 130 — after 296 CPU tests passed. `tests/test_checkpoint.py` has two regression tests using a stand-in whose `.numpy()` fails until `.cpu()` is called; they fail without the fix.
- **Pattern: three separate CUDA-only faults have now shipped past a green CPU suite** (metrics device mismatch in `evaluate.py`, CuPy HD95 in `Trainer.validate`, RNG restore here). The Mac is a correctness harness for *logic*, not for device placement. Any code that touches `.numpy()`, a device transfer, or a MONAI metric should be read with "what if this tensor is on CUDA?" in mind, because no local test will ask that question.
- **Never pass CUDA tensors into `compute_case_metrics` / `add_case`.** MONAI's `compute_hausdorff_distance` computes its distance transform via **CuPy** when the inputs are on CUDA, and on the Kaggle T4 image that CuPy JIT fails outright: `CompileException: Thrust requires at least C++17` (measured 2026-08-01). The CPU path uses scipy and has no such dependency. Both `Trainer.validate` and `scripts/evaluate.py` therefore `.cpu()` prediction and target before scoring — which also keeps HD95's intermediates over a ~240³ volume off the 16 GB VRAM budget. This bug is invisible on the Mac: on CPU the tensors are already on CPU, so all 296 tests pass either way.
- **`inference.sliding_window.output_device` is MONAI's `device` kwarg, not its `sw_device`.** MONAI has both: `device` is where the stitched full-volume output accumulates, `sw_device` is where each cropped window runs through the model. The config field is deliberately *not* named `sw_device` because the two are trivially confusable. Setting it to `"cpu"` means `sliding_window_predict` returns a CPU tensor, on purpose.
- **`et_min_volume` exists and is off.** Zeroing a small ET prediction entirely scores Dice 1.0 on cases with no ground-truth enhancing tumor under `ignore_empty=False`, buying headline ET Dice without the model being any more accurate. On BraTS 2021 that is only 2.6% of cases (see the measured note above), so the trick buys far less here than the folklore suggests — which makes turning it on even harder to justify. It launders exactly the overconfidence the calibration claim is supposed to expose. Turn it on only to reproduce someone else's number, and say so if you do.
- **`NeuroVisionX.forward` now has THREE return types, and eval mode must always be the `Tensor` one.** `MultiTaskOutput` when `self.training and heads.has_auxiliary`; `list[Tensor]` when `self.training and deep_supervision_levels > 1`; `Tensor` otherwise. Sliding-window inference and MONAI's inferer call `model(patch)` and assume a tensor — returning anything else breaks every evaluation path with no shape error, just a wrong Python type flowing downstream. `tests/test_neurovision.py` pins the eval-returns-Tensor case with both auxiliary heads on. This also makes the MC-dropout hazard worse: enabling dropout via `model.train()` can now hand you a `MultiTaskOutput` where inference wants a tensor, so enable the `Dropout3d` modules individually (they now live in the auxiliary heads too) and leave the model in `eval()`. `build_neurovision` guards the pairing the same way it guards deep supervision: auxiliary heads enabled ⟺ `training.loss.name == "multitask"`, raising in either direction. The reverse case matters — `multitask` with no auxiliary heads silently reduces to the plain segmentation loss while the config claims otherwise.
- **MONAI's `HausdorffDTLoss` is built and registered but OFF by default (`training.loss.multitask.surface.enabled: false`), for two measured reasons.** It computes a Euclidean distance transform for BOTH prediction and target on EVERY forward. On CUDA that goes through `monai.transforms.utils.distance_transform_edt`, whose `use_cp` branch requires cuCIM/CuPy — the exact backend that already failed on the Kaggle T4 image with `CompileException: Thrust requires at least C++17` for HD95. Without cuCIM it falls back to scipy, i.e. a host round-trip: **measured 0.72 s per step** for the 24 transforms a 4-patch × 3-channel × 96³ batch needs, roughly doubling step time. The boundary HEAD gets a comparable signal for the price of two `max_pool3d` kernels. Turn `surface` on only as a deliberate ablation row.
- **`morphological_boundary` uses `max_pool3d`, whose padding is `-inf`, so erosion IGNORES out-of-patch neighbours rather than treating them as background.** Measured, not assumed: an all-ones mask yields an exactly empty shell (no border rim), and a tumor touching a patch face gets no shell at that face. That is the behaviour you want for 96³ crops — a tumor cut by the patch edge is not really bounded there, it continues outside the crop. An earlier version of this reasoning had it backwards and would have justified a spurious border shell on every patch.
- **The confidence head's target is computed under `no_grad` from the segmentation logits, and that detach is load-bearing.** No gradient reaches the segmentation head through the confidence term; it reaches only the shared decoder features that the confidence head reads. If the segmentation logits took gradient from the confidence objective, the model could lower that loss by becoming *uniformly* confident — exactly the overconfidence the calibration claim exists to expose. `tests/test_multitask_loss.py` pins it with a leaf-tensor backward asserting a zero/absent grad.
- **Multi-task loss weights are NOT normalized to sum to 1, unlike `DeepSupervisionLoss`.** Segmentation stays at exactly 1.0 so its gradient is identical across ablations; otherwise "did the boundary head help?" is confounded with "did the effective segmentation LR change?". Starting point `seg 1.0 / boundary 0.3 / confidence 0.05 / surface 0.0`. Rationale for the magnitudes: region Dice+BCE settles ~0.25 while the thin-shell boundary Dice stays ~0.7 (the shell is ~2% of voxels and is intrinsically harder), so equal weights would let the boundary term quietly dominate late in training — precisely when Dice is being decided, and the paper needs *competitive Dice* alongside better boundaries. Confidence is small because its target moves (it depends on the segmentation head's current correctness) and because it is meant as a read-out, not a co-objective. **Caveat that partly defeats the non-normalization:** `grad_clip_norm: 1.0` scales the WHOLE gradient down once the norm exceeds it, which does change the effective segmentation LR. `Trainer` therefore logs `train/grad_norm` (free — `clip_grad_norm_` returns the pre-clip norm) alongside `train/loss_<term>`. If the multi-task run clips routinely where the seg-only baseline did not, raise `grad_clip_norm` rather than rescaling the weights.
- **No warmup ramp on the confidence weight, deliberately.** A step counter inside the loss is state the checkpoint does not save, so it would restart on every 12-hour Kaggle resume and make the objective depend on how many times the session was killed — a silent violation of hard constraint 4. A small constant weight instead.
- **No differentiable-ECE term on the segmentation logits, deliberately.** It would optimize the metric the paper reports. "Better calibrated architecture" and "trained to minimize ECE" are different claims and the second is much weaker; it would also contaminate comparison against baselines that lack it. The confidence head is safe in this respect because reported ECE is measured on the segmentation probabilities, which the confidence objective never touches.
- **`MultiTaskOutput` is a plain `@dataclass`, never a `NamedTuple`.** A NamedTuple is iterable, so `DeepSupervisionLoss` would happily iterate it and treat the `confidence` field as a logits tensor. A dataclass has no iteration protocol, so a caller written for the wrong return type raises immediately instead of silently computing something wrong.
- **Both auxiliary heads attach ONLY to decoder stage 0 (full resolution), never to deep-supervision levels.** A 1-voxel boundary shell at stride 4 is mostly aliased away, and a downsampled correctness map is not a correctness map. `tests/test_auxiliary_heads.py` asserts the auxiliary outputs carry `feats[0]`'s spatial shape — that is what catches a head wired to the wrong decoder stage, which no shape assertion elsewhere would notice. Cost: each head keeps ~4 feature-map-sized tensors alive for backward at the widest resolution, ≈0.2 GB per head at 96³/4 patches/fp16, ~0.45 GB for both. Real but affordable at `batch_size: 1`.
- **Each auxiliary head reads its OWN config sub-block.** They carry identical values today, which makes collapsing them into one shared parameter set tempting — do not. `model.head.boundary.hidden_channels` would then be read and thrown away, building a head of a different width with no error anywhere. Config keys that are read but not honoured are the failure mode the "config objects passed in, never global state" rule exists to prevent.
- **`sliding_window_predict` calls `model.eval()`, and `nn.Module.eval()` RECURSES into children — so the obvious MC-dropout implementation is silently deterministic.** Enable the dropout submodules, then call the existing sliding-window helper N times, and every one of those calls switches them straight back off before the forward pass runs. Result: N identical passes, mutual information exactly 0 everywhere, a plausible-looking uncertainty map that means nothing, and no error anywhere. Fixed with a `set_eval: bool = True` parameter whose only intended caller is `mc_dropout.py`. Verified by reverting the fix: `tests/test_mc_dropout.py::test_n5_stochastic_model_gives_positive_mutual_information` was **the only test in that file that failed** — every other one checks internal arithmetic consistency of whatever came back, which holds whether or not the passes were genuinely stochastic. Do not delete it.
- **Active dropout modules do NOT prove the MC passes differed, and `zero_init_residual` is a live instance of the gap.** Measured on the production config: `mc_dropout_predict` on a freshly-built `NeuroVisionX` reports 10 active `Dropout3d` modules and still returns `mutual_information == 0` at every voxel, with different seeds giving bitwise-identical output. Cause: `zero_init_residual: true` zeroes `norm2.weight` in every `ResidualBlock`, so the residual branch outputs exactly 0 at init, and `Dropout3d` sits *before* `conv2 -> norm2` — its perturbation is multiplied by that zero and annihilated. `norm2.weight` moves off zero after one optimizer step, so a **trained** checkpoint is unaffected; this only bites on an untrained or barely-trained model. Confirmed by flipping the flag: `zero_init_residual=false` gives MI max 0.0367. `require_dropout` cannot catch this (it only counts modules), so `mc_dropout_predict` additionally *warns* when `mutual_information.max() == 0` at `num_samples > 1`. A warning and not an exception: at N=1 MI is 0 by construction, and a uniformly confident model on an easy volume can legitimately produce a near-zero epistemic map.
- **The CNN encoder is currently the ONLY source of MC-dropout stochasticity.** `model.encoder.cnn.dropout: 0.1`; `model.head.dropout`, `model.decoder.dropout`, and both fusion dropouts are all `0.0`, and `SegmentationHead`/`AuxiliaryHead` build an `nn.Identity()` rather than a `Dropout3d(p=0)` when their probability is 0, so those do not even appear in `count_active_dropout`. Decide whether head/decoder dropout should be non-zero **before** the calibration runs — it is a training-config change, so it cannot be retrofitted to an existing checkpoint.
- **MC-dropout uncertainty is per-channel Bernoulli, NOT categorical BALD.** The three output channels are overlapping regions with independent sigmoids, so the usual softmax BALD formula does not apply. Per channel: predictive entropy `H[p̄]` (total), expected entropy `E_t[H[p_t]]` (aleatoric), mutual information = the difference (epistemic). Units are nats; the Bernoulli maximum is `ln 2 ≈ 0.693`, not 1. Reported per channel and never pooled — ET is the region the calibration claim leans on.
- **Mutual information is biased LOW at small N, so never compare MI across runs with different `num_samples`.** `p̄` from N samples is a noisier estimate of the true predictive mean, and entropy is concave, so `E[H(p̄_N)] <= H(p̄_∞)` — the total term is underestimated while the aleatoric term (an average of N already-unbiased per-pass entropies) is not. Bias shrinks roughly as `1/N`. A "lower epistemic uncertainty" reading could just mean a smaller N.
- **`MCDropoutOutput.mean_prob` is PROBABILITIES, breaking the convention that everything in `neurovision.inference` returns logits.** Necessary, not stylistic: the correct MC estimate is `mean(sigmoid(logits_i))`, and `sigmoid(mean(logits_i))` is a different quantity because sigmoid is nonlinear. The hazard: `postprocess_logits` applies its own sigmoid, so feeding it `mean_prob` double-sigmoids and shrinks everything toward 0.5. Use `logits_from_mean_prob`, which clamps away from 0/1 first (`logit(0)` is `-inf`, and an inf reaching the component filters yields NaN). Safe because `logit` is strictly monotone, so it does not change which voxels discretize as foreground — it only makes the existing filtering and nesting logic reusable.
- **MC-dropout accumulates, never stacks.** Two running float32 accumulators (`sum_prob`, `sum_entropy`) sized like one pass. Measured against the real 1251 cases: median cropped volume (137, 171, 140), so a 3-channel fp32 full-volume buffer is ~39 MB — two accumulators are ~78 MB regardless of N, versus ~390 MB at N=10 for a stack that grows linearly. Cost is exactly N× a single sliding-window pass: median **12 windows/case** at roi 96 / overlap 0.5 (max 36), i.e. 3 batched passes at `sw_batch_size: 4`, so N=10 is ~120 windows / ~30 batched passes per case. `num_samples: 10` is the literature standard and affordable; N=50+ is not on ~30 rationed hours a week.
- **`skimage`'s `remove_small_objects` is deprecating `min_size` in favour of `max_size`, with flipped semantics** — the new parameter removes objects smaller than *or equal to* its value, the old one only smaller. `min_component_size: 50` currently drops 49-voxel components and keeps 50-voxel ones; after that migration the same number would drop 50 too, shifting every reported HD95. Deps are pinned, so this is dormant — check it before bumping scikit-image.
